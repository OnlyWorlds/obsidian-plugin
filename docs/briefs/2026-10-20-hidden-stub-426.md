## Why

keel's hidden mark (the one rule, Keel #421) lets a world's owner hide an element from everyone but the owner, the co-builders and its creator. It is built on keel, switched off, and turns on in one moment soon. When it is on, a member's plugin (a contributor's or a guest's key) meets three new things: a feed delete row with `reason: "hidden"`, a 409 `resync_required` carrying `reason: "role"` or `"view"`, and a 404 on a hidden id exactly like a missing one. Owners and co-builders see none of this (they read everything).

## Today's behaviour (read; confirm in the code)

A delete row never deletes a note: Download keeps it, lists the id in `settings.deletedOnServer` so a save never re-creates it, and says "N elements deleted on the server — their notes were kept. Remove them manually if desired." A 409 `resync_required` makes the deleted-list read say it cannot tell (`reason: "resync"`).

## What ships

1. **A hidden row stubs the note.** On a feed delete row whose `reason` is `"hidden"`, Download rewrites that element's note, through the one writer, as a stub: the element's fields (frontmatter fields and the field sections the note format writes) are emptied, a line "Hidden by the world's owner." stands where they were, and everything the person wrote that is not an element field is kept byte for byte. If the note format cannot tell the person's writing from the element's own text sections, keep the whole body, empty only the frontmatter's element fields, and say so in your report. A note already a stub is left alone (idempotent). The id goes into a per-world list beside `deletedOnServer` (`hiddenOnServer`), consulted wherever the deleted list is: a save or an export never re-creates or re-sends it, and a save on a stubbed note refuses with a notice "Hidden by the world's owner: not saved." An upsert of the id later in the feed (an unhide) takes it off the list and the next Download writes the note in full again, as for any element.
2. **Counted apart.** The download notice says hidden notes in their own sentence, never in the deleted count: "N elements were hidden by the world's owner; their notes now hold only your own writing." A delete row with no reason or `reason: "deleted"` stays exactly today's path.
3. **The 409's reason.** Read `reason` from the error envelope (inside `error`, or beside it: accept either). After the resync walk from the start: `role`, or no reason at all (keel with the mark off): keep every note, change nothing but what the walk upserts (D128's text: "keep what you hold that the new walk does not name"). `view`: each element note of that world the fresh walk does not name becomes the stub of item 1 and is counted with the hidden ones ("N elements left your view; their notes now hold only your own writing."). Never delete a note file in any case; never stub a note that has no element id (a person's own note).
4. **Words.** Every new string in sentence case. The repo's README or docs page that describes Download's deletes gains two sentences on hidden elements; no CHANGELOG or release notes (I write those at release).
